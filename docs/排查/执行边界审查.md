动态邮箱脚本需要在原有发码动作前增加 `request = case.scout.otp_request(account)`，取码改为 `case.scout.otp(account, request=request)`。请求仅存当前 Case 内存，一次消费、最长 90 秒；同收件人重新准备、整例重跑、reset、进程重启都会使旧请求失效。固定码沿用旧调用；新代码尚未安装到正在运行的 Scout。

## 已修复：同一执行多账号破坏资源凭据集合

优先级 P1，归属 Nexus。

- 原 `resources/resource_claim_tx.py:claim_in_transaction` 每次申请都重新创建 `epochs`，最后覆盖 `request.resource_epochs`；同一 attempt 先领取账号 A，再领取 B 时，请求凭据只剩 B 和设备。
- 现在每次认领合并 `resource_epochs`，设备、每个 slot 账号及其当前账号池租约在同一次执行中保持完整；续租、持久派发恢复、资源卡和终态清理都遍历全部 slot。
- 账号身份不再通过单一 `picked_account` 表达；`leased_accounts` / `leased_account_leases` / `leased_account_by_slot` 是事实集合，旧字段只作兼容视图。

原问题曾在内存模拟中复现：两次申请均成功，但第二次后 `_attempt_rows(...)[1]` 为 false，资源键为 `account:p:accountA, account:p:accountB, device:phone`，请求凭据键仅为 `account:p:accountB, device:phone`。

修复采用“同时保留多个 slot 账号”的语义，不提供同一 slot 静默换号。slot 重复调用是幂等读取；scope 变化明确返回 `account_slot_scope_mismatch`；租约丢失返回 `resource_account_missing`。这样账号池租约、ExecutionResource 和持久 admission 凭据不会被一个 slot 的后续申请覆盖。

## 仍然存在的外部关联边界

邮箱 UID 边界可以排除准备之前已收到的旧邮件，但无法区分准备后延迟到达的上一次邮件与本次发码邮件。严格区分需要被测产品邮件携带可匹配的发码请求标识；当前接口不能凭收件人和时间推断它。没有真实邮箱复测证据，不能宣称所有错码场景已消除。

## 为什么最近集中暴露

本轮发现的共性是同一个事实有多份表示，却没有在恢复、复用、换号和兼容路径中保持一致：账号缓存与号池租约、资源表与 epoch 凭据、调试进度与正式准入、文档与运行时。

Git blame 显示资源凭据覆盖逻辑来自 2026-10-22 的 `16dcf0fc`；账号缓存路径可追溯至 2026-10-30，相关分支在 2026-11-16/17 调整过。这支持“旧缺陷与近期边界改动共同暴露”的判断，但不能代替发布版本及线上记录对照，不能认定所有问题均由最新版本引入。
