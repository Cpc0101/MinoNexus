## 本轮已修复

| 问题 | 修复 | 验证 |

| 邮箱取码按整个用例起始时间筛选，可能命中未消费旧邮件 | 发码前 `otp_request(account)` 捕获 UIDVALIDITY/UIDNEXT，取码携带 request；只接受边界之后的邮件 | 旧 UID 被排除、新 UID 可取；缺请求、重复使用、跨账号/会话、过期及邮箱代际变化均阻塞 |

| Scout 架构文档仍写重启后允许重跑一步 | 修正文档：遗留执行 interrupted，未知写保持隔离，不自动重放 | 与现有持久记录/代际设计对齐 |

动态邮箱脚本需要在原有发码动作前增加 `request = case.scout.otp_request(account)`，取码改为 `case.scout.otp(account, request=request)`。请求仅存当前 Case 内存，一次消费、最长 90 秒；同收件人重新准备、整例重跑、reset、进程重启都会使旧请求失效。固定码沿用旧调用；新代码尚未安装到正在运行的 Scout。

## 新确认、尚未修复：同一执行更换账号破坏资源凭据集合

优先级 P1，归属 Nexus。

- `resources/resource_claim_tx.py:claim_in_transaction` 每次申请都重新创建 `epochs`，最后覆盖 `request.resource_epochs`。
- 同一 attempt 先领取账号 A，再领取 B 时，资源表仍保存 A、B、设备三项，但请求凭据只保存 B 和设备。
- `casework/execution_resources.py:_attempt_rows` 要求资源表集合与请求凭据集合完全一致，因此下一次续租验证失败。
- 终态清理也校验资源 epoch 归属；丢失的凭据可能进一步使资源保留，不能通过忽略 epoch 校验解决。

内存模拟调用真实 `claim_in_transaction` 两次，保留真实模型对象，替换数据库与时间预算/写保护外部依赖。结果：两次申请均成功；第一次 `_attempt_rows(...)[1]` 为 true，第二次为 false。资源键为 `account:p:accountA, account:p:accountB, device:phone`，请求凭据键仅为 `account:p:accountB, device:phone`。

修复应明确“同时保留多个账号”和“释放旧账号后换号”的语义，让账号池租约、ExecutionResource 和持久 admission 凭据在同一事务中一致更新。不能仅把字典覆盖改为合并：旧账号的号池租约可能已在换号时释放，续租仍会失败。

## 仍然存在的外部关联边界

邮箱 UID 边界可以排除准备之前已收到的旧邮件，但无法区分准备后延迟到达的上一次邮件与本次发码邮件。严格区分需要被测产品邮件携带可匹配的发码请求标识；当前接口不能凭收件人和时间推断它。没有真实邮箱复测证据，不能宣称所有错码场景已消除。

## 为什么最近集中暴露

本轮发现的共性是同一个事实有多份表示，却没有在恢复、复用、换号和兼容路径中保持一致：账号缓存与号池租约、资源表与 epoch 凭据、调试进度与正式准入、文档与运行时。

Git blame 显示资源凭据覆盖逻辑来自 2026-10-22 的 `16dcf0fc`；账号缓存路径可追溯至 2026-10-30，相关分支在 2026-11-16/17 调整过。这支持“旧缺陷与近期边界改动共同暴露”的判断，但不能代替发布版本及线上记录对照，不能认定所有问题均由最新版本引入。
