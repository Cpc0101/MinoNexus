# 常见问题

按「现象 → 看什么 → 根因 → 处理」组织。执行已经下沉到 Scout 脚本，所以**大部分失败码来自脚本执行，不再有守卫/熔断那一套**。

先看 [Session日志与数据库](Session日志与数据库.md) 拿到 `session_id`，再按下面查。

---

## 1. 任务一开跑就失败（没进设备）

`execution_started=no`，`failure_stage=admission`。看 `case` 上的 `reason_code`：

| reason_code | 含义 | 处理 |
|---|---|---|
| `script_repo_missing` | 项目还没配脚本仓库 | Workbench 项目设置里填仓库地址与分支 |
| `project_scope_invalid` | 用例不属于该项目 | 核对用例归属 |
| `node_offline` | 持有该 `sn` 的节点不在线 | 启 Scout；或换一台在线设备 |
| `task_cancelled` | 开跑前已取消 | — |
| 资源类 | 账号 / 设备 / 写安全未通过 | 看 [用例密钥与租约](../专题/用例密钥与租约.md) |

## 2. 下发成功但 Scout 没执行

`script_no_result` 或 `declined`：

| 现象 | 看 | 处理 |
|---|---|---|
| `declined` + 缺渠道 | Scout 的 `REGISTER.executors[].available` 与 `reason` | 在该节点装对应渠道程序（adb / Chromium） |
| `declined` + `run_id` 对不上 | `script_dispatch` 的准入记录 | 节点不是持有该 `sn` 的那台，或用旧 `run_id` 重放 |
| `script_no_result` | Scout 日志（`ScriptDispatch`） | 脚本进程挂了或超 deadline |

## 3. 脚本执行失败

`failure_stage=run`，失败码写在会话的 `tool/result`：

| reason_code | 含义 | 处理 |
|---|---|---|
| `locator_missing` | 该渠道没有这个控件的定位单元格 | 在 `pages/<APP_KEY>/<page>.yaml` 补该渠道的 `locator_spec` |
| `control_unknown` | 页面文件里没有这个控件 | 检查 `page_key.control_id` 拼写，或补控件 |
| `script_step_missing` | 步骤编号缺失 / 无效 | 用例里 `with case.do(n)` 的 `n` 要来自原文 |
| `revision_missing` | 取不到指定提交 | 核对 `revision`，或留空取分支最新 |
| `model_unconfigured` | 节点没配模型地址 / 模型名 / 密钥 | 在 Scout 本机配置模型服务 |
| `otp_environment_unavailable` | 无固定码且本节点未配 Gmail 收信 | 配固定码或配 Gmail 收信 |

**页面文件位置不对**是最常见的一类：必须是 `pages/<APP_KEY>/<page_key>.yaml`，目录名等于 `config.yaml` 里的 key。放在 `pages/` 根下会被直接拒绝（`页面文件要放在 pages/<APP_KEY>/ 下`）。

## 4. 定位对不上 / 点错

| 现象 | 原因 | 处理 |
|---|---|---|
| `on_page` 失败 | 锚点文案在该渠道界面上不匹配 | 换更稳定的锚点（控件 id 优于文案） |
| 点在错误元素 | `locator_spec` 命中多个 | 用 `cardinality` 与 `index` 收紧 |
| 只有一个渠道失败 | 该渠道单元格缺失或写错 | 只改该单元格，**不要复制一份用例脚本** |

不要用整屏搜索文案绕过页面文件。定位缺失就当缺失处理。

## 5. Web 渠道特有

| 现象 | 看 | 处理 |
|---|---|---|
| 页面结构全空 | `hierarchy` 的 `nodes` 是否为空 | 确认 Chromium 已装、页面已 ready |
| 输入不进框 | `input` 的 `params` | Web 走 `enrich_web_input_text_params`，需要焦点确认 |
| 截图是空白帧 | `shot_is_blank` | 页面还没渲染完，加 `case.wait` 或换等待条件 |
| 并发互抢 | lane 分配 | 每个 run 独占一个 lane，第 5 个排队 |

详见 [Web适配](Web适配.md)。

## 6. 模型相关

| 现象 | 看 | 处理 |
|---|---|---|
| 脚本里 `case.llm` 报未配置 | `model_unconfigured` | 在**该节点**配 base_url / model / key |
| 模型返回空 | Scout 日志的 HTTP 状态 | 端点、额度、`response_format` 支持情况 |
| Nexus 侧 LLM 报未配置 provider | `platform/settings_store` 的 `ai-user:<uid>` | Workbench 设置里给**当前执行账号**配 key 并勾选「允许跑用例」 |

**没有环境变量 Key 兜底。** `MINO_AI_API_KEY` 已不参与用户执行；缺 Key 就是缺 Key，不会借用管理员或别人的配置。

## 7. 结束但结果不可信

`write_outcome_unknown` → 写动作没有回执，结果收口为 `blocked`，设备与账号**保持隔离**。处理：

1. 在设备上看真实状态（是否真的点了 / 真的提交了）。
2. 用 baseline 复核后解除隔离，**不要直接判通过**。
3. 不要重放同一步试图刷成绿色。

## 8. 查不到会话

| 现象 | 处理 |
|---|---|
| `session_meta` 不存在 | 开跑就没过准入，查 `app_regression_runs` 里该 case 的 `status` 与 `reason_code` |
| 会话存在但没有 `tool/result` | 脚本在第一个设备动作前就失败了，看 `node/enter` 与 `case.fail` |
| 重启后历史消失 | 查错了库：开发 `~/.mino-dev/nexus/mino.db`，正式 `~/.mino/nexus/mino.db` |

## 9. 节点与实例

「本机只有一个 Scout，开发与生产实例必须分开」这类问题的判断方法见 [Scout进程与实例边界](Scout进程与实例边界.md)。

## 10. 5 分钟排查流程

1. `session_meta` → 一句话 summary + `reason_code`。
2. 按 `seq` 顺序看最后一个 `tool/call` 与它的 `tool/result`。
3. 失败码在上表里定位处理方向。
4. 涉及定位 → 直接看 `pages/` 文件和该渠道的单元格。
5. 涉及租约 / 隔离 → [用例密钥与租约](../专题/用例密钥与租约.md)。
6. 改完配置**重启对应进程**：改 Nexus 代码重启 Nexus，改脚本仓库不用重启。
