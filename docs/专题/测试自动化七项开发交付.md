通用阶段观察和对象验证在 Scout SDK `mino_scout.runtime.business_state`；生成模板随 `mino_scout.templates.script_repo.flows` 分发。实际脚本仓直接 import SDK，将生成模板放入 flows，并由应用 flow 配置已采集的页面/组件/对象信号。没有通用硬编码的 Hi3D 定位，也不把业务阶段放入账号池。原文映射、整例编排及最终预期在各自用例中；源模板不自动补数、换号或重复写入。具体应用的定位与阶段规则是否准确需发布后用 Scout 证据验收。

Agent 通过 Nexus MCP 的 agent_workflow_init/start/finish/resolve/get 记录调查，按登录用户与 workflow_id 隔离。真源是当前 Nexus SQLite 数据库，不在 Agent 或 Scout 创建进度库。它约束调查轮次，不能取代用户授权、Nexus 资源约束或 Scout 测试判定；普通任务查询不占新调查预算。源码和安装副本的更新分别处理，本次没有安装或替换用户的已安装技能。

账号长期业务数据继续存入当前 Python SQLite 的独立关系表，不另引入数据库。数据记忆与标签辅助选号；未记录不等于数据不存在，不增加库存认证、充足性证明或流程引擎。

同时修正了一项影响新安装的既存迁移问题：历史 im_inbox_items 没有当前模型或消费者，移出必建表清单，旧表与数据保留。实际 startup/ensure_db 的全新临时库初始化、版本 10/11 到 12 的账号数据与 Agent 进度表升级及重复初始化已验证。

验证使用 `/tmp/remaining_logic_smoke.py`、`/tmp/agent_workflow_smoke.py`、`/tmp/fresh_schema_smoke.py`、已有 runtime/statistics Python fixtures 和 `/tmp/account_ui_contract.mjs`，均为临时目录、内存数据库或模拟页面，没有连接真实被测应用，也没有修改团队数据库。检查包括 Python 编译、Nexus 分层（0 违规）、协议及文档两仓一致、Workbench verify/build、源技能校验和 Git diff 格式检查。Workbench 全仓 lint 为 0 error、5 条已有 Hook warning，本次新增界面与 API 文件无 lint finding。

发布后验收顺序：main 打包 → 核对并部署/安装对应产物 → 查看台账和需求分页 → Scout 实际验证生成阶段与指定对象跨页/跨应用关联 → 缺口准备/续跑 → 探针/准备与正式统计报告对照。每次保留 task/session/attempt/revision、原文预期和执行时间，后续成功不覆盖旧任务。
