# 测试账号数据需求与准备方案（讨论稿）

日期：2026-11-17。本文按本次讨论修订。首批实现账号数据记录、申请需求留存、业务标签偏好分配及 Agent 指引；运行时动态定位继续使用 Scout 既有能力，复杂业务 flow 由脚本仓按具体应用维护。

当前目标是让测试持续推进：有数据就使用，需要的数据缺少时构造，再继续原用例。账号标签和资产记忆辅助选数，不增加“库存充足、库存完整或全部资产已核验”的开跑门禁。原文要求的业务结果仍在实际使用和验证步骤中检查，不能将执行放行记为测试通过。

**一、四类数据各自负责什么**

| 内容 | 作用 | 保存位置 |
|---|---|---|
| 账号标签 | 注册、登录、会员等账号业务状态，辅助匹配账号 | Nexus 账号资源 |
| 账号资产记忆 | 记录测试中见过、创建过或使用过的模型、图片、订单等对象，方便下次复用 | Nexus 独立资产记录；与账号关联 |
| 运行时对象绑定 | 保存本次操作产生或选中的具体对象，在后续页面、弹窗和应用中继续使用 | Scout 脚本变量或本次运行上下文 |
| 业务阶段与检查逻辑 | 根据当前页面、组件、元素和绑定对象识别阶段、定位、等待及检查 | 脚本仓 `flows/` |

账号标签不承担整套资产数据的长期记忆。长期记忆帮助找到数据，运行时绑定保证本次后续操作始终使用预期的具体对象。

**二、第一步：轻量记录和复用，账号正常分配**

Nexus MCP 接收账号申请时可以同时记录“需要什么数据”的说明，并用标签和已有资产记录辅助选择更合适的账号。没有记录、记录不全、记录没有命中或对象状态未知，都不能单独成为业务执行阻塞原因。

分配先满足项目、环境、身份和租约等既有账号约束。业务标签与资产记忆优先用于偏好排序；没有最匹配账号时，继续使用可分配的账号，数据缺口交给 Agent 处理。避免把可构造的数据条件写进必须满足的账号过滤条件，导致反复申请仍拿不到账号。

资产记录先只保存使用所需的最小信息，例如：

- 账号、应用、环境、对象类型；
- 对象 ID 或其他可重定位的引用；
- 名称及少量用于区分对象的特征；
- 测试中已经观察到的业务状态；
- 记录时间和来源会话引用。

不做全量盘点，不要求账号资产完整，不先建设容量评估、有效期证明或复杂可用性评分。写入的是实际观察或创建所得的信息，不能编造资产来满足匹配。

候选对象在使用时发生变化或找不到，flow 返回当前观察和具体缺口；Agent 决定复用其他数据或构造所需数据，再更新相关记忆；不因此进入“重新申请账号—匹配失败—继续等待”的循环。

**三、第二步：修改用例编写策略，缺数据时主动构造**

默认流程为“分配账号 → 使用已知数据或当前可找到的数据 → 缺少时构造 → 绑定具体对象 → 继续业务步骤 → 验证结果”。

Agent 在编写和调试时说明输入数据从哪里来、怎样准备以及产物引用。缺数据自动构造只属于 Agent。脚本仓不写 get_or_create、缺数据自动补数或换账号策略；flow 只执行明确操作并返回对象、阶段及观察。缺口由脚本记录，Agent 在授权范围内准备后再推进。

原文显式要求生成模型时，可调用 create_model 业务操作并将产物保存到 model_ref；原文仅需要模型作为输入时，Agent 先准备或选定输入，正式脚本使用明确引用。函数名是概念示例，不是新增通用运行时 API。

构造可以包括填写表单、上传输入素材、生成模型、创建订单或其他用例所需数据，但必须服务于当前测试目标。用户提出的标签或分组也可辅助管理；除非原文就是测试标签行为，否则不能把“先建好某个混合标签”加入通用执行前置。

如果生成模型本身是原文要测试的行为，就在该操作步骤执行并绑定产物；如果模型只是输入数据，则由 Agent 决定准备路径，通过单独的 Scout 准备脚本执行明确生成操作。共享流程不改变原文操作顺序，也不通过另选无关对象掩盖自动带入等业务失败。

已尝试的创建路径出现明确失败时，保留原因并选择有依据的替代准备方式；结果不明时先查本次创建任务或当前对象，避免重复生成。已有授权范围内能解决的数据缺口由 Agent 继续处理。真正不可完成的动作应输出具体缺口、尝试结果和下一步，不能无限等待，也不能伪造业务数据或通过结论。

**四、运行时数据绑定与动态对象定位**

先生成或选择对象，再将其标识和特征保存到明确变量。后续定位和验证使用该对象变量，不写死某条历史模型名称、固定列表序号或第一个卡片。

对象引用可以由 ID、名称、类型、创建标记、时间或其他本次观察到的特征组合构成。有业务 ID 时优先使用；没有可读取 ID 时用足以区分对象的特征。不要为了统一格式强迫所有应用提供同一种字段。

| 难度 | 数据流 | 需要保留和重新定位的内容 |
|---|---|---|
| 1 | 单页面 | 创建或选中对象后，在本页读取和操作同一对象 |
| 2 | 弹窗或组件结构改变 | 保留对象引用；结构变化后重新读当前控件并匹配对象 |
| 3 | 跨页面 | 将上一页对象引用传给目标页 flow，在目标列表、详情或预览中重新定位并比较 |
| 4 | 跨应用 | 从 A 的结果生成 B 可识别的业务引用或映射，传给 B 的 flow 并验证对象关系 |

动态的是对象数据及其页面表示。页面结构、容器和组件关系仍可用于缩小定位范围。切页或重绘后保留业务值，重新读取当前节点；不把旧 DOM、坐标或节点句柄当成跨页稳定对象。

“模型自动带入”的验证应比较输入 `model_ref` 与商详实际对象。存在模型卡片、打开选择器或手工选中另一个模型，都不能替代这一比较。

**五、flows 维护可复用业务状态和验证方法**

`flows/` 不仅封装点击序列，还应承载可复用的业务阶段识别、明确业务操作、对象绑定、动态定位、等待和检查方法。例如模型生成 flow 根据当前页面、组件和元素状态区分输入就绪、设计生成中、设计可用、模型生成中、模型可用及明确失败。

阶段判断来自该业务的当前观察，可根据页面动态更新。不能仅凭一个固定按钮文案，或全局存在 `Download` 就判定整个生成过程成功。该业务应能判断下载入口属于参考图、设计图还是模型，并返回相关对象和观察。

定位依据当前应用、平台和页面的真实节点及交互属性。不能因为几个应用都使用 button，就将所有可操作元素限制为 `role=button`；也不能因文字相同就点击不可交互的标题。多候选时组合页面范围、组件关系和对象特征定位。

用例负责“这条原文要做什么、验证什么”及其 `source_ref`；flow 负责“怎样完成、识别、等待和检查这类业务”。复用验证方法时，实际结论仍关联本用例的输入对象、当前观察和原文条目，不把共享函数变成按 case_id 分发整条用例的中央调度器。

第 5、7、9 类问题应按这一结构一起处理：绑定输入对象，业务 flow 返回阶段及实际对象，复用检查方法比较数据和 UI 状态，再记录原文预期的判定。比如“不新开标签”比较操作前后的标签集合；“不出现旧弹窗”检查相应弹窗；“购买按钮可点击”检查实际交互状态。

**六、约束和提醒覆盖 Agent 全流程**

| 阶段 | 应具备的机制 |
|---|---|
| 理解需求 | 区分原文前置、输入数据、被测行为和辅助管理方式；不要自行把标签变成必需前置 |
| 分析人工用例 | 记录数据的生产者和消费者、对象关联，以及哪些用例可复用同一业务 flow |
| 设计脚本 | 明确 Agent 的数据准备方案与脚本的输入契约、运行时变量、业务阶段判断和验证方式 |
| 编写脚本 | 提醒复用已有 flow；避免写死账号资产、首个卡片、全局按钮角色或整段生成等待 |
| 调试执行 | 每轮确认新观察、具体失败点及下一步；相同阻塞重复时改变解决路径，不无进展重跑 |
| 阶段交付 | 分别展示需求分析、脚本实现、数据准备和正式验证的完成度，继续推进不依赖同一阻塞的工作 |
| 汇报结果 | 从结构化结果和明确的 task/session/attempt 生成状态及时间，不从自由文案推测 |

本轮已同步 Agent guide 与 `analyze-test-case`、`write-test-cases`、`run-test-cases` 源技能；共享 flow 的状态观察和 app 断言已可通过现有静态检查。当前“共享 helper 只做操作”的约束应明确允许复用业务状态、对象绑定及检查方法；原文映射、用例特定预期和正式结论仍可在单用例文件核对。

不为本期再引入重型流程引擎或全量数据资格校验。优先用普通 Python flow、明确返回值、运行时变量和可读提示解决已暴露的问题。

**七、独立处理的 bug**

- 探针主动结束被计为正式用例失败：执行用途、诊断完成状态和正式断言结果分别表达；原文未执行不能计为通过或产品失败。
- 报告状态、任务数量和时间口径不一致：固定报告所引用的任务与会话，使用真实状态和同一时间窗口；较早的生成过程不能标成最新探针过程。

前者涉及执行结果契约与统计，后者涉及 Agent 报告生成及汇总逻辑。两项都应独立修复，不能依靠账号资产记忆解决。

**八、存储与职责**

先沿用现有 D1，采用独立、轻量的关系记录保存账号资产记忆。账号标签继续记录账号业务状态；对象详细数据不堆进 `facets_json`，账号备注不作为正式资产台账。

本期只需增加资产记录与账号的关联；数据需求可以随申请或任务记录。不要先建设复杂库存审核、完整性证明或准备任务资格系统。数据库迁移另行根据实际规模和查询需要评估。

Nexus MCP 负责账号、资产记忆查询与写入、请求信息和已有任务调度。Scout 通过脚本执行目标 UI。脚本仓 flows 负责业务操作、阶段判定、运行时绑定；缺数据后的构造与恢复决策只归 Agent；Nexus 不保存运行中的页面句柄，也不接管下一步 UI 决策。完整执行证据保持在 Scout。

**前三项源码落地（2026-11-17）**

1. Agent 数据准备闭环：`case.data.require` 返回具体 `data_missing`，Agent guide 与执行源技能明确「读取缺口→选择明确准备脚本→核对输出→保存台账→新任务续跑」。`case_run.case_inputs/source_context` 固定输入并记录 prepare/resume 与父任务关系，校验发起用户、项目和环境。Nexus 不执行造数决策，flows 不内置自动补数或换号。准备任务独立统计，原任务结论保留。
2. 资产记忆辅助选号：新增 `resource_account_select`，按 kind/object_ref/attributes 的精确子集偏好排序空闲账号；申请账号回调支持 `data_requirements`。无匹配记录仍保留候选；登录身份、环境、锁定与租约保护仍有效。`case_inputs.account_id` 固定准备与续跑的同一账号，不把业务对象堆入标签。
3. 运行时对象与动态定位：`case.data.bind/get/inputs` 管理有界业务值；对象输出和缺口随 Scout 记录持久化，并进入 Nexus 每例摘要。已绑定对象在进程中断后仍可读取，封存输出不能被改写。`app.bind` 从本次变量填充定位模板，动作与断言重新解析当前结构；CSS 转义、Web 角色与作用域、原生唯一节点定位、跨 app 临时控件键隔离均已接入。重复候选不默认取首项。

已完成隔离契约验证：实际 Scout 运行时的缺口/显式准备/续跑与本地记录，Python SQL 台账幂等与偏好回退、选号 HTTP 响应，D1 全迁移后的任务准入/派发输入/结果同步/父任务范围/重复请求幂等/租约保护；模拟页面覆盖重绘后重新定位、跨 app 重新绑定、角色定位、重复候选拒绝和 CSS 转义，原生覆盖 Android 重复节点与 iOS 精确查询。以上均为临时数据库和模拟对象，不能当作被测业务 UI 通过。
