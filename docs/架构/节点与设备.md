# 节点与设备

Nexus 只有 `sn`（设备标识）是不够的：多节点下必须区分「哪台机器上的哪台设备」。`node_id` 就是为此引入的一层。

## 1. 两个层级

```
node_id = 一台跑着 MinoScout 的机器（= scout_id，[a-z0-9]{16}）
   └── devices[] = 这台机器能操作的设备
        ├── sn: R5CT30xxxx       Android（adb）
        ├── sn: 00008030-...     iPhone（ios_wda）
        └── sn: web{node_id}     Playwright 虚拟槽（每个节点一个）
```

| 概念 | 稳定性 | 说明 |
|---|---|---|
| `node_id` | 重启不变 | 变了就等于换了一台机器 |
| `sn` | 跟设备走 | adb serial / iOS UDID / `web`+`node_id` |
| `web{node_id}` | 跟节点走 | Playwright 虚拟槽。旧名 `web-local` / `web_local` 仅作升级残留 |

**没有 `remote` 通道，也没有 `claw-*` 设备**（ClawNode 已于 2026-11 删除）。

## 2. 归属

设备记录的 `channels` 里带 `node_id`：

```json
{
  "node_id": "abcdefghijklmnop",
  "adb": {"state": "connected", "transport": "usb", "serial": "R5CT30xxxx"}
}
```

Nexus 派单时按 `sn` 反查节点（`resources/node_registry.py: resolve(sn)`），拿到该节点当前的连接对象再发 `EXECUTE`。**同一台设备不要挂在两个 Scout 节点上**——归属唯一，重复挂载行为未定义。

## 3. 连通性只来自 Scout

`REGISTER` / `HEARTBEAT` 是唯一真源。Nexus **不探测设备**，也不缓存「设备可用」的本地结论：

| 事实 | 来源 |
|---|---|
| 节点在线 | WS 连接存活 + 心跳 |
| 设备上下线 | `HEARTBEAT.device_delta` |
| 通道可用性（adb 已授权 / Chromium 已装） | `REGISTER.executors[]` 的 `available` 与 `reason` |

无节点在线时 Nexus 必须能正常启动，并在 UI 上说清楚「没有可用节点」。

## 4. 派单

| 场景 | 选择依据 |
|---|---|
| 脚本运行 | 用例绑定的 `sn` → 持有它的节点 |
| 单动作 `EXECUTE` | `sn` + `platform` + 该设备已连通通道 |
| Scout 安装 / 升级 / 渠道安装 | 用户名下、当前在线的节点 |

`EXECUTE.device_hint` 只带事实：`env`、`app_id`、`adb_serial` / `udid` / `model`。**不下发绝对路径、模型密钥、账号密码。**

## 5. 设备会话（`device_app_sessions`）

记录「这台设备上这个应用当前是不是登录态」。它是**登记簿**，不是实时真值：

- 用例开跑时 `session_dirty=1`，`session_fact=unknown`，**不继承**其他用例的 inspect 结论。
- prep 收工时信任**本任务**的 inspect 结果；`dirty` 时不信登记簿单独下的结论。
- 真实登录态由 Scout 在执行中上报（登录态探针），不是 Nexus 猜的。

## 6. 相关表

| 表 | 说明 |
|---|---|

| `device_reservations` | 设备预约 |
| `device_resource_leases` | 设备资源租约 |
| `scout_updates` | 节点更新任务 |
