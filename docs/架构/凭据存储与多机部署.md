# 凭据存储与多机部署

本文只说明**测试资源账号池中的 `password` / `otp`**。AI Provider、渠道密钥、Scout Gmail、插件密钥等其他系统密钥仍走各自的配置与信任边界，不能因为本文而视为已经统一加密。

## 结论

- Workbench 是纯 Web 应用，不需要 Electron、macOS Keychain 或浏览器钥匙串。测试账号密码只在用户提交表单时短暂经过页面内存和 HTTPS 请求，不写入 `localStorage`、`IndexedDB` 或 Service Worker。
- Nexus 是测试账号凭据的唯一真源。数据库只保存 AES-256-GCM 密文，主密钥不进入 `mino.db`，也不随数据库备份传播。
- 普通账号列表、详情、MCP、模型上下文、日志、导入预览和证据快照只返回 `has_password` / `has_otp` 等配置状态，不回传密码或 OTP 明文。
- 自动执行只有在账号存在有效租约、应用范围匹配且执行通道经过认证时，才为当前账号按字段解密；人工 OTP 查询要求具有项目维护权限并显式传入 `app_id`。
- **多机部署尚未实现。** 当前 Nexus 仍是单机 SQLite 架构。多机不能靠把 `mino.db` 放到共享盘或让每台机器各存一份账号密码来解决；正确方向是共享数据库加统一 KMS / Secret Manager。

## 1. 信任边界

| 位置 | 持久化凭据 | 可见内容 | 约束 |
| --- | --- | --- | --- |
| Workbench 浏览器 | 否 | 用户正在填写的表单值 | 必须使用 HTTPS；登录页和账号页不得记录请求体 |
| Nexus API 进程 | 仅进程内存 | 请求字段、当前租约账号所需字段 | 授权校验通过后才解密；不得写普通日志 |
| Nexus 数据库 | 仅密文 | `enc:v1:...` | 数据库备份不能单独恢复出明文 |
| 主密钥存储 | 是，且独立于数据库 | AES-256 密钥或 KMS 密钥引用 | 生产环境不得自动生成，不得打进镜像或仓库 |
| MCP / 模型 | 否 | 配置状态和脱敏元数据 | 不提供密码回读工具 |
| Scout / 执行通道 | 否 | 当前租约账号本次所需字段 | 必须校验租约、应用范围和通道身份 |
| 运维审计 | 否 | 读取、展示、预留、释放、更新事件 | 审计记录不得包含凭据值 |

字段级加密降低的是“数据库文件、备份或 SQL 查询泄露后直接看到密码”的风险。它不能阻止拥有 Nexus 进程、主密钥和数据库权限的攻击者解密，也不能替代 HTTPS、RBAC、XSS 防护、终端安全和访问审计。

## 2. 账号生效应用

账号必须显式绑定一个或多个应用：

- 新账号默认勾选当前应用，不再提供“全部应用”产品语义。
- `app_ids` 必填、去重，至少一项、最多 100 项，且必须属于当前项目。
- 已有账号可以单独编辑生效应用，但存在未释放租约时不能改范围。
- 历史 `app_ids=[]` 只表示“未关联应用”，不解释为全部应用，也不参与选号和租约领取。
- 列表、详情、OTP、预约、候选排序、模板分配、恢复和实际租约领取都要求显式 `app_id` 并校验范围。

应用范围是准入条件，不是展示标签。业务数据偏好、模型建议或请求中的其他条件都不能放宽 `app_ids`。

## 3. 当前加密实现

### 3.1 算法与格式

- 算法：AES-256-GCM。
- 每个字段使用独立随机 12 字节 nonce。
- 密文格式：`enc:v1:<key_version>:<base64url(nonce+ciphertext)>`。
- AAD 绑定 `project_id`、`account_id`、字段名、密钥版本和 schema 版本。复制密文到其他项目、账号或字段后无法正常解密。
- 空值保持空字符串，加密字段不做密文截断。

当前 keyring 是**部署级全局 keyring**，支持一个 active key 和多个历史 key version。还没有实现 per-project DEK、KMS envelope encryption 或按项目撤销密钥。

### 3.2 密钥来源

以下来源互斥，不能同时配置：

| 环境变量 | 用途 |
| --- | --- |
| `MINO_NEXUS_CREDENTIAL_MASTER_KEY` | 直接提供 base64url 编码的 32 字节密钥 |
| `MINO_NEXUS_CREDENTIAL_MASTER_KEY_FILE` | 从文件读取密钥；拒绝符号链接和 group/world 可读文件 |
| `MINO_NEXUS_CREDENTIAL_KEYS_JSON` | 多版本 keyring，JSON 对象为 `{版本: base64url 密钥}` |
| `MINO_NEXUS_CREDENTIAL_KEY_VERSION` | 指定 active key version，默认 `1` |

开发模式在未配置显式密钥时，会自动生成 `<data_dir>/secrets/credential-master.key`，目录权限为 `0700`，文件权限为 `0600`。生产模式缺少密钥时 fail closed，不会静默生成新密钥。

生产环境应优先从 KMS / Secret Manager 注入短期可用的密钥材料或完成解密，不要把长期主密钥写进 shell 历史、仓库、镜像、Compose 文件或数据库。

### 3.3 明文生命周期

1. Workbench 在内存中收集表单值，通过 HTTPS 提交。
2. Nexus 完成身份、项目和字段校验。
3. 写库前在进程内存中加密；数据库只收到密文。
4. 列表和详情不读取 `password` / `otp` 字段的明文，只返回是否已配置。
5. 自动执行成功领取租约后，按当前账号需要的字段解密并交给执行上下文。
6. 人工 OTP 查询只在项目维护权限和应用范围校验通过后，取单个账号的 `otp`；Gmail 等外部取码路径不回传密码。

历史明文仍可只读兼容，但任何新写入都会变成密文。应尽快完成一次性迁移并妥善处置迁移前备份。

### 3.4 迁移与检查

迁移必须停止 Nexus，避免迁移期间继续写入明文或产生不一致状态：

```bash
mino-nexus credential status  --data-dir <数据目录> --mode production
mino-nexus credential migrate --data-dir <数据目录> --mode production --dry-run
mino-nexus credential migrate --data-dir <数据目录> --mode production
mino-nexus credential status  --data-dir <数据目录> --mode production
```

正式迁移前会通过 SQLite backup API 生成一致备份。`status` 只输出空、密文、明文三类计数，不输出项目、账号、密钥或字段值。备份在迁移前可能仍包含历史明文，确认迁移和恢复演练完成后应按生产数据保留策略安全销毁。

## 4. 多机部署应该怎么做

### 4.1 不采用“每台机器同步密码文件”

以下方案都不应使用：

- 每台 Workbench 或 Nexus 自己保存一份账号密码。
- 把 SQLite 文件放在 NFS / SMB 共享盘，让多个实例直接读写。
- 每台机器放同一份明文 master key，再靠复制数据库同步。
- 依赖 Electron / 操作系统钥匙串作为服务端唯一凭据源。

SQLite 适合当前单机部署，但它的文件和锁语义不适合多主机强一致写入；共享盘还会放大锁、延迟、备份和故障恢复问题。

### 4.2 目标拓扑

```text
Workbench 静态站点
        │ HTTPS
        ▼
负载均衡 / API Gateway
        │
        ├── Nexus 实例 A ─┐
        ├── Nexus 实例 B ─┼── 共享 PostgreSQL / MySQL
        └── Nexus 实例 C ─┘          │
                                      └── KMS / Secret Manager

Scout ──认证通道──► Nexus 实例
```

关键原则：

1. **账号不复制，只共享一个逻辑真源。** 多台机器看到的是同一数据库中同一行账号，不需要做客户端或主机间“密码同步”。
2. **Nexus 实例尽量无状态。** 会话、租约、任务、应用范围、审计和密文都在共享持久层；负载均衡不应依赖 sticky session 才能保持正确性。
3. **数据库只保存密文。** 账号更新、租约领取和范围校验在事务中完成；领取账号必须使用行锁或等价的原子条件更新，避免两个实例同时租到同一账号。
4. **所有实例读取同一 keyring。** 主密钥由 KMS / Secret Manager 管理，明文只在进程内存驻留必要时间；KMS 不可用时 fail closed。
5. **备份与密钥分离。** 数据库备份、对象存储和日志不包含 master key。恢复时必须重新接入 KMS，不能依赖备份内藏密钥。
6. **审计跨实例统一。** 记录查看 OTP、凭据读取、账号预留/释放、应用范围变更、密钥版本切换和失败原因；审计中只存账号 ID 和操作结果，不存密码或 OTP。

### 4.3 推荐的密钥分层

多机生产环境建议升级为 envelope encryption：

- KMS 持有不可导出的 KEK。
- 每个项目生成随机 DEK；数据库保存 KMS 包裹后的 DEK 和版本。
- 账号密文使用对应项目的 DEK，AAD 继续绑定 `project_id/account_id/field/key_version`。
- Nexus 在通过权限、租约和应用范围校验后，按项目向 KMS 解包 DEK，并限制缓存时间。
- 轮换时新增密钥版本并重加密；旧版本在完成迁移和回滚窗口后再撤销。
- 项目删除或合规撤销时，使对应 DEK 失效，避免只删业务行却留下可恢复密文。

这是目标方案，不是当前实现。当前代码只有部署级 keyring，尚无 KMS 调用、per-project DEK、分布式密钥缓存或项目级撤销。

## 5. 从当前版本上多机的顺序

1. **先收紧单机安全**：生产显式配置 keyring、HTTPS、CORS、访问控制、日志脱敏、历史明文迁移和备份销毁演练。
2. **抽象持久层**：把当前硬编码 SQLite engine、SQLite 专用 upsert / `BEGIN IMMEDIATE` 和迁移逻辑改为可测试的数据库适配层。
3. **迁移到共享数据库**：选择 PostgreSQL 或 MySQL，完成 schema、事务、行锁、索引、备份恢复和数据迁移；不能只改一个连接字符串。
4. **引入 KMS / Secret Manager**：实现 KEK、per-project DEK、密钥版本和多实例一致性读取；密钥不可用时拒绝凭据读写。
5. **验证并发准入**：两个实例同时争抢同一账号时只能有一个成功；应用范围更新与租约领取不能穿透事务边界。
6. **再横向扩容 Nexus**：前置负载均衡，执行滚动升级；确认 WebSocket、Scout 回调、任务恢复、租约与审计不依赖进程本地状态。
7. **补齐运维能力**：密钥轮换、备份恢复、灾难恢复、审计保留、容量告警和权限复核。

## 6. 当前实现边界

已经实现：

- 账号应用范围必选、多选、默认当前应用、可编辑，并由后端强制校验。
- `password` / `otp` 的 AES-256-GCM 字段级加密。
- 历史明文只读兼容和新写入加密。
- 列表、详情、日志、快照、导入预览和 MCP 读结果的凭据脱敏。
- 配置化全局 keyring、多 key version、开发自动密钥和生产 fail closed。
- 迁移 dry-run、状态统计、一致备份和 CLI 入口。

尚未实现：

- PostgreSQL / MySQL 等共享数据库适配与迁移。
- KMS / Secret Manager、per-project DEK、项目级密钥撤销。
- 多 Nexus 实例、负载均衡、HA、故障转移。
- 跨实例分布式锁或完整的数据库租约并发验证。
- 多机同步、密钥轮换自动化和在线迁移控制面。

因此，当前版本可以支持“多个用户从不同机器打开同一个 Workbench 并访问同一个 Nexus”，但不能把多个 Nexus 服务实例各自启动后当成一套高可用系统运行。
