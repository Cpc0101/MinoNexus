# 能力目录

能力目录是 **Nexus 独有**的资产，Scout 不读它。它声明「能做什么、用什么实现」，**不写「什么时候做、按什么顺序做」**。

运行时真源是 `mino.db` 的 `catalog_entries`。程序直接派发的系统能力在 Nexus 启动时由代码注册与升级（`startup.py`），**不要求用户在 Workbench 点升级**；业务能力由 Workbench `/packs` 维护。

## 1. `kind` 的取值

以 `catalog/exec_classes.py` 为准，**只有四种**：

| kind | 含义 |
|---|---|
| `check` | 预期类动作，任意阶段可执行 |
| `generic` | 通用动作，任意阶段可执行 |
| `recovery` | 模型无法继续时、或屏幕不可用时使用 |
| `base` | 平台基座（平台入口与提供面），**不进模型菜单** |

`MENU_ATOMIC_KINDS = check + generic + recovery`，菜单与派单读同一份。历史文档里的 `abstract_cap` / `executor` / `capability` / `resource` 都不存在。

## 2. 一行目录有什么

`models/catalog.py: CatalogEntry`，唯一约束 `(kind, id)`：

| 列 | 说明 |
|---|---|
| `kind` / `id` | 主键组合 |
| `enabled` / `lifecycle` | 停用与生命周期（`active` 等） |
| `ui_coverable` | 是否允许 UI 覆盖 |
| `platforms_json` | 该能力适用的平台集合 |
| `visible_to_json` | 可见范围 |
| `exec_class` | 执行类 |
| `payload_json` | `implementations` / `provides` / `requires_caps` / recovery 规则等 |

## 3. 实现路径怎么写

一条能力可以有多个实现路径，每个路径声明 `executor` 与 `runs_on`：

```json
{
  "implementations": [
    {"id": "tap.adb", "executor": "adb", "runs_on": "scout", "platforms": ["android"]},
    {"id": "tap.ios_wda", "executor": "ios_wda", "runs_on": "scout", "platforms": ["ios"]}
  ]
}
```

**executor id 固定为** `adb` / `ios_wda` / `playwright` / `mac` / `win`（`desktop` 只作旧载荷入站别名）。`remote`（ClawNode）已删除。

## 4. 本地执行器（不出网）

`catalog/exec_classes.py: LOCAL_EXECUTOR_IDS` 是**唯一名单**，菜单过滤与派发都读它：

```
lease_account, get_otp, get_phone, release_account,
operation.check_box, dismiss_ime, confirm_login_state,
assert_visual, persona_subtask, wait_ms, wait_screen_ready,
signal_nav_calib_step, run_flow_block,
note, sample
```

未知能力**不要**往这份名单里加——加了等于让 Nexus 本地装作能执行设备动作。

## 5. 启动时注册的系统能力

`startup.py` 在启动时调用（代码声明，不是常量改完就完事，必须连平台一起维护）：

| 模块 | 注册什么 |
|---|---|
| `catalog/evidence_seed.py` | 证据类能力 |
| `catalog/self_prove_seed.py` | `self_prove`（Android `self_prove.adb`，iOS `self_prove.ios_wda`） |
| `catalog/recovery_seed.py` | recovery 规则 + 当前本地能力 |
| `catalog/resource_transition_seed.py` | 资源状态迁移规则 |
| `catalog/flow_block_seed.py` | 全局逻辑块 |
| `catalog/skill_channel.py` | 程序直接派发的渠道能力 |

## 6. 改一条能力

| 你要做的 | 改哪里 |
|---|---|
| 加一条业务能力 | Workbench `/packs`，或改对应 `*_seed.py` 后重启（已有行不会自动覆盖） |
| 换实现路径（同一平台换 executor） | 改该行 `payload_json.implementations`，**Scout 侧零改动** |
| 加一种设备通道 | 新增一个 executor 行 + Scout 侧一个实现类，已有能力自动获得新路径 |
| 新增一个平台 | 同时改 `platforms_json`、`exec_classes.py` 名单（若属本地执行器）、`contract/executors.py` 映射 |

## 7. 与执行的关系

`script.run` 链路**不使用** `executor_order` 选路——脚本自己按 `pages/` 的 `locator_spec` 定位，Scout 按 `platform` 取单元格。能力目录仍然服务：

- 普通单动作 `EXECUTE`（设备诊断、宿主插件、`self_prove` 等）
- Workbench 的 `/packs`、`/flow-blocks` 页面
- `router_proxy` 的本地能力判定（`is_local_cap`）
